# 서버 — AWS 인가 홈서버인가, 그리고 API 로 가르면 얼마인가

지금 앱은 서버가 없다. 카드 그림만 Supabase Storage 에서 받아 오고, 나머지는 전부
사용자 Mac 안에서 끝난다. 이 문서는 **무엇을 서버로 옮길지**, **어디에 둘지**,
**얼마나 걸릴지**를 정한다.

전제: 사용자는 **나와 테스터 몇 명**이다. 이 전제가 비용 계산을 거의 다 정한다.

## 1. 지금 무엇이 급한가

Supabase 무료 한도가 **저장 1GB · 전송 2GB/월** 이다.

| | 지금 |
|---|---:|
| 작은 카드 그림 17,662장 | 433MB |
| 큰 카드 그림 1,284장 | 198MB |
| 팩 아트 137개 | 8MB |
| **버킷 합계** | **640MB** |

저장은 아직 여유가 있다. 문제는 **전송**이다. 한 사람이 컬렉션을 처음부터 끝까지
훑으면 441MB 가 나간다 — **다섯 번이면 월 한도**다. 앱이 디스크에 캐시하므로 같은
사람의 반복 조회는 괜찮지만, 테스터가 서넛만 돼도 첫 달에 닿는다.

## 2. 서버가 맡을 네 가지 — 성격이 전혀 다르다

| | 하는 일 | 필요한 것 |
|---|---|---|
| 가 | 이미지·데이터 배급 | 오브젝트 저장소 + CDN. 코드 없음 |
| 나 | 세이브 동기화 | 계정 + DB + API |
| 다 | 뽑기를 서버가 굴림 | 위 + **앱의 중심을 뒤집는 개편** |
| 라 | 랭킹·공유 | 위 + 집계 + 공개 웹페이지 |

「가」는 파일을 어디에 두느냐의 문제라 하루 이틀이면 끝난다. 「다」가 나머지 전부를
합친 것보다 크다.

## 3. 먼저 말해야 할 것 — **뽑기를 서버로 옮겨도 조작은 못 막는다**

「다」의 목적이 조작 방지라면, 이 앱에서는 성립하지 않는다.

재화가 **사용자 Mac 의 AI 도구 사용량 로그를 읽어서** 나온다. 서버는 그 로그를 볼 수
없고, 앱이 「오늘 2억 토큰 썼다」고 신고하면 믿는 수밖에 없다. 뽑기를 서버가 굴려도
**입금을 조작하면 그만**이다. 자물쇠를 금고에 달고 벽을 종이로 두는 셈이다.

그래서 「다」의 값어치는 이렇게 봐야 한다.

- **얻는 것** — 세이브 파일을 손으로 고쳐 카드를 늘리는 것은 막힌다. 뽑기 결과가
  기기와 무관하게 재현되고, 확률 공시가 서버 기록으로 증명된다
- **못 얻는 것** — 사용량을 부풀리는 조작. 랭킹을 진지하게 매기려면 이쪽이 본질이다

랭킹을 넣을 거면 **사용량에 기대지 않는 지표**(도감 완성 수, 특정 세트 수집률)로 잡거나,
조작 가능성을 인정하고 가볍게 가는 편이 낫다.

## 4. 어디에 둘 것인가

가진 것: **집 Mac 서버**(이미 켜져 있음), **Route 53 도메인**(이미 쓰는 중), Tailscale.

### 비용은 어느 쪽도 0 이다

| | 증분 비용 | 근거 |
|---|---:|---|
| 집 Mac | **0원** | 전기는 이미 쓰고 있다 |
| AWS | **0원** | 도메인·DNS 가 이미 나가는 돈이다. 나머지는 무료 한도 안 |

AWS 를 실제로 계산하면 S3 0.64GB 가 월 $0.02, CloudFront 는 **월 1TB 무료(영구)** 라
열 명이 컬렉션을 통째로 훑어 4.4GB 를 써도 한도의 0.4% 다. Lambda 100만 요청·DynamoDB
25GB 도 영구 무료다. 도메인 값이 이미 지출된 이상 **AWS 도 사실상 공짜다.**

**그래서 비용은 결정 요인이 아니다.** 무엇이 덜 귀찮은가로 정한다.

### 이미지는 집에서 내보내지 않는다 — 이건 확정

카드 그림이 17,662장 441MB 다. 캐시가 빈 사람이 컬렉션을 훑으면 그만큼이 **집 업로드
회선**으로 나가고 그동안 집 인터넷을 다 문다. 객체가 1만 7천 개라 앞단 캐시를 둬도 잘 안
쓰이는 것부터 밀려 계속 다시 올라간다.

**S3 + CloudFront 에 둔다.** 이미 있는 Route 53 도메인에 서브도메인 하나만 붙이면 되고,
DNS 를 다른 데로 옮길 일이 없으며, 무료 한도가 200배 남는다. 올리는 스크립트는 이미
있다(`upload_supabase.py` 의 대상만 바꾼다).

### API 를 어디에 둘 것인가 — 셋 중 하나

집 Mac 을 밖에서 닿게 하려면 공개 주소가 필요하다. 여기가 갈린다.

**가. 집 Mac + Tailscale Funnel** — 0원, 오늘 바로 된다
: 포트를 열지 않고 인증서도 자동이다. 대신 주소가 `*.ts.net` 로 고정이고(커스텀 도메인
  불가), 대역폭 한도가 공개돼 있지 않다. API 는 요청이 작아 문제되지 않는다.

**나. 집 Mac + Cloudflare Tunnel** — 커스텀 도메인이 되지만 **도메인 NS 를 통째로 옮겨야 한다**
: Cloudflare 무료·Pro 플랜은 **서브도메인만 위임하는 것을 지원하지 않는다.** 즉
  `api.내도메인.com` 하나 때문에 도메인 전체의 네임서버를 Route 53 에서 Cloudflare 로
  옮겨야 하고, 지금 쓰는 레코드를 다 옮겨 심어야 한다. Route 53 별칭(alias) 레코드를
  쓰고 있다면 CNAME 으로 바꿔야 한다. **이 하나를 위해 치를 값이 아니다.**

**다. AWS Lambda** — 기존 도메인 그대로, 집과 무관하게 항상 떠 있다
: 증분 0원이고 정전·이사·약관에서 자유롭다. 대신 Swift 를 Lambda 에 올리려면 커스텀
  런타임이나 컨테이너 이미지를 한 번 엮어야 하고, 로컬에서 돌려 보는 맛이 Mac 에서
  직접 돌리는 것만 못하다.

**권함: 이미지는 S3+CloudFront, API 는 「가」(집 Mac + Tailscale Funnel).**
DNS 를 하나도 안 건드리고, 있는 기계를 쓰고, Swift 가 네이티브로 돈다. 주소가 `*.ts.net`
인 것이 걸리면 나중에 「다」로 옮기면 되는데, 앱의 서버 주소는 이미 설정으로 바꿀 수 있게
돼 있어서 그때 코드를 고칠 일이 없다.

### 남는 위험

- **집이 죽으면 동기화와 랭킹이 죽는다.** 이미지와 데이터는 CloudFront 에 있으므로 그동안에도
  카드는 뜬다 — 이 구성이 피해를 그만큼 줄여 준다
- **가정용 인터넷 약관.** KT 는 승인 없는 서버 설치를 금지 항목으로 적고 있다. Funnel 은
  포트를 여는 것보다 눈에 덜 띄지만 약관상 안전해지는 것은 아니다. 트래픽이 작으면
  현실적인 문제는 되지 않는다

## 5. 서버를 무엇으로 만드는가 — **Swift**

게임 규칙이 전부 `import Foundation` 만 쓴다. 확인했다.

```
PackOpening · GameState · CardIndex · MarketEconomy · Oripa · DexIndex · DexProgress · CardPrices
```

AppKit 도 SwiftUI 도 안 들어간다. 즉 **서버가 앱과 같은 소스 파일을 그대로 쓸 수 있다.**
팩 확률표, 100원 단위 계산, 도감 판정을 두 번 적지 않아도 되고 두 벌이 조용히 갈라지지도
않는다. 이 앱에서 가장 자주 어긋난 것이 「같은 계산을 두 곳에 적어 둔 것」이었다.

호스트가 Mac 이라 **Swift 가 그 기계의 1급 언어**이기도 하다. 크로스 컴파일도 컨테이너도
필요 없다.

구성 제안: **Hummingbird + SQLite.** 사용자가 열 명이면 Postgres 를 세울 이유가 없다.
파일 하나라 백업이 곧 복사이고, 나중에 커지면 그때 옮긴다.

Spring Boot 가 더 익숙하시지만 그 이점을 규칙 재구현 비용이 상쇄한다 — 확률표와 경제
계산을 Kotlin 으로 옮겨 적고, 앞으로 밸런스를 고칠 때마다 두 벌을 맞춰야 한다.

## 6. 작업 견적

| # | 단계 | 무엇을 하나 | 크기 |
|---|---|---|---|
| 1 | 정적 배급 | 이미지를 S3/R2 로 옮기고, 데이터 파일에 판번호를 붙여 앱 재배포 없이 갱신 | **2~3일** |
| 2 | 계정 | Sign in with Apple, 사용자 표, 토큰 검증 | **3~5일** |
| 3 | 세이브 동기화 | 오프라인 우선 + 두 Mac 충돌 해소 | **1.5~2주** |
| 4 | 뽑기 서버화 | 구매·개봉·판매·오리파를 API 로. 앱의 중심이 뒤집힌다 | **3~4주** |
| 5 | 랭킹·공유 | 집계 배치 + 공개 페이지 | **1~1.5주** |
|   |  | **합계** | **7~9주** |

### 4번이 왜 큰가

지금은 팩을 사는 것이 `wallet.spend()` 한 줄이다. 서버로 옮기면 이렇게 된다.

- **네트워크가 없으면 어떻게 할 것인가.** 메뉴바 앱은 늘 떠 있고 인터넷은 끊긴다.
  「끊기면 못 연다」로 두면 지하철에서 앱이 죽고, 「끊기면 로컬로 연다」로 두면 서버화의
  뜻이 없어진다. 큐에 쌓았다가 올리는 절충이 현실적이고, 그 큐가 곧 새 결함 원천이다
- **재화 장부가 두 곳이 된다.** 사용량은 로컬에서 계속 늘고 지출은 서버가 기록한다.
  둘을 맞추는 규칙을 새로 정해야 한다
- **UI 가 전부 기다림을 갖는다.** 즉시 반응하던 화면에 실패·재시도·지연이 생긴다
- **테스트 703개 중 상당수가 로컬 지갑을 전제한다**

### 무엇을 먼저 해야 하는가

**1번만 먼저 하는 것을 권한다.** 지금 실제로 아픈 것(전송 한도)이 그것뿐이고, 2~3일이면
끝나며, 나머지를 하든 안 하든 어차피 필요하다. 덤으로 시세를 앱 재배포 없이 갱신할 수
있게 된다 — 지금은 시세 한 번 바꾸려고 판올림을 내야 한다.

2·3번은 「Mac 을 두 대 쓰기 시작하면」 필요해진다. 4·5번은 **랭킹을 정말 낼 것인지**
정한 뒤에 손대는 것이 맞다. 3절에서 적었듯 조작 방지가 목적이라면 값어치가 생각보다 적다.

## 7. 지금 결정할 것

비용은 어느 쪽도 0 이라 결정 요인이 아니다. 남는 것은 넷이다.

1. **1번만 먼저 할 것인가, 전부 갈 것인가** — 1번은 2~3일이고 지금 아픈 곳을 고친다
2. **API 를 집 Mac 에 둘 것인가 Lambda 에 둘 것인가** — 4절 「가」와 「다」
3. **서버 언어** — 규칙 공유를 노리면 Swift, 익숙함을 택하면 Kotlin
4. **랭킹을 낼 것인가** — 4·5번의 존재 이유다. 3절에서 적었듯 조작 방지가 목적이라면
   값어치가 생각보다 적다

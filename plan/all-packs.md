# 전체 팩 추가 — 계획

작업 전 앱은 10세트 1,284장을 싣고 있었다. 수집해 둔 전체 174세트 20,479장 가운데 실제
팩으로 구성할 수 있는 것을 선별해 싣는 계획으로 시작했다.

**로테이션은 이번에 하지 않는다.** 130개 팩을 전부 상시 판매한다.

숫자는 전부 `data/` 의 실제 파일, API 표본 조사, 앱을 20,544장 규모로 돌려 잰 값이다.

## 구현 결과 (2026-09-01)

- 팩으로 구성 가능한 **122세트 17,666장**을 번들에 실었다
- 17,666장 전부 시세가 있고, 카드명도 17,666장 전부 한국어로 표시된다
- 한국 공식 카드와 같은 일러스트를 대조한 결과는 별도 표로 보존하고, 공식 대응이 없는
  이름은 번역 fallback으로 표시해 공식명이 생기면 자동으로 교체되게 했다
- 상점은 시리즈별 목록 → 세트 격자로 나눴고, 팩 그림은 대표 그림만 먼저 받은 뒤 해당
  시리즈에 들어갈 때 나머지를 받는다
- 값순 정렬과 오리파 후보 선반은 인덱스 생성 때 한 번 계산하고 재사용한다
- 시대별 실물 팩 구조와 봉입률은 `real-pack-odds.md`에 따로 정리했다

검증 결과는 `swift test` 698개 통과(선택형 성능 테스트 9개 스킵), 로직 코어 라인 커버리지
89.12%, release 앱 빌드 성공이다.

## 1. 시세는 전부 받을 수 있다 — 확인함

### 요청하신 사이트는 쓸 수 없다

`collectory.cc/robots.txt` 가 **모든 에이전트에 `/api/` 를 금지**한다(`User-Agent: *` 포함).
v0.4.0 때 조사한 결과와 같다. 시세를 긁어 오는 용도로는 쓰지 않는다.

### 지금 쓰는 곳이 전 시대를 덮는다

`api.pokemontcg.io`(TCGplayer 미국 시세)를 1999년부터 2025년까지 시대별로 13세트, 1,726장을
표본 조사했다.

| 세트 | 발매 | 카드 | TCGplayer | Cardmarket |
|---|---|---:|---:|---:|
| Base | 1999/01 | 102 | 99% | 100% |
| Base Set 2 | 2000/02 | 130 | 100% | 100% |
| Neo Destiny | 2002/02 | 113 | 100% | 100% |
| Team Rocket Returns | 2004/11 | 111 | 100% | 100% |
| Secret Wonders | 2007/11 | 132 | 100% | 100% |
| HS—Unleashed | 2010/05 | 96 | 100% | 100% |
| Burning Shadows | 2017/08 | 177 | 95% | 100% |
| Evolving Skies | 2021/08 | 237 | 100% | 100% |
| Scarlet & Violet | 2023/03 | 250 | 100% | 100% |
| Journey Together | 2025/03 | 190 | 100% | 100% |
| Mega Evolution | 2025/09 | 188 | 100% | 0% |

**표본 전체 TCGplayer 99%.** 옛날 세트가 더 잘 나온다 — 오래 거래된 카드라 값이 두껍다.
가장 최신 세트만 Cardmarket 이 비는데 TCGplayer 로 덮인다.

**결론: 130개 팩 전부 시세를 붙일 수 있다.**

### 다만 API 가 불안정하다

표본 13세트 중 2세트가 `500`·`502` 로 실패했다가 재시도에서 붙었다. 그리고 파이썬 기본
User-Agent 는 `403` 으로 막힌다. 수집 스크립트에 **재시도와 User-Agent** 를 넣어야 한다.
API 키는 없지만 무인증 한도(하루 1,000회) 안에 든다 — 174세트면 250회 안팎이다.

## 2. 팩이 되는 세트는 130개다

등급을 매핑해 세트별로 세면 이렇다.

- **125개** — 정상 팩(커먼이 있고 카드가 충분하다)
- **37개** — 커먼이 없다 → 지금의 「특별 팩 4장」 경로
- **47개** — 매핑 카드 20장 미만. 대부분 프로모 모음이라 애초에 팩이 아니다

팩 아트 슬러그가 137개 확보돼 있는 것과 대체로 맞는다.

## 3. 한국어 — 전부 한국어로 낸다

세트마다 사정이 다르다.

| | 장수 | 방법 |
|---|---:|---|
| 한국 출시 카드 | 약 14,862 | `data/ko-meta`(한국 세트 181개)와 **일러스트레이터 + 번호**로 결합. v0.3.2 때 쓴 방식 그대로 |
| 한국 미출시 카드 | 약 5,600 | 정식 명칭이 없으므로 **번역해서 넣는다** |

미출시분은 대부분 옛 WotC 시절 세트와 프로모다. 카드 이름은 거의 포켓몬 이름이므로
**종족 이름 표(`data/species-ko.json`)로 대부분 덮인다.** 트레이너·에너지 카드처럼 종족이
아닌 것만 손으로 옮기면 된다.

원칙을 정해 둔다.

- 정식 한국어명이 있으면 **반드시 그것을 쓴다**. 번역이 정식 명칭을 덮으면 안 된다
- 정식 명칭이 없을 때만 번역한다. 어디가 번역인지 데이터에 표시해 두어, 나중에 정식 명칭이
  생기면 그 자리만 갈아 끼울 수 있게 한다
- 검증 대조군을 만든다. v0.3.2 때 97.4% 로 맞춰 본 방식을 규모만 키운다

## 4. 번들 크기 — 팩 아트만 결정이 필요하다

| 파일 | 지금 | 전체 |
|---|---:|---:|
| card-index.json | 44KB | 650KB |
| card-prices.json | 24KB | 340KB |
| card-names-ko.json | 41KB | ~700KB |
| **팩 아트** | 615KB | **10.5MB** |

앱 zip 이 2.2MB 다. 팩 아트를 그대로 담으면 **13MB** 가 된다. 카드 그림은 이미 네트워크로
받아 캐시하므로 팩 아트도 같은 길로 보낸다. 그러면 번들 증가가 1.7MB 로 끝난다.

## 5. 성능 — 데이터만 늘리면 안 된다

20,544장 규모로 실제로 돌려 쟀다.

| | 값 | 할 일 |
|---|---:|---|
| 인덱스 디코딩 + 값순 정렬 | **0.54초** | 정렬 순서를 빌드 때 파일에 박는다 |
| 컬렉션 첫 레이아웃 | 7.8ms | 없음(격자가 게으르다) |
| 화면 갱신 1회 | **33ms** (지금 4.9ms) | 세트·등급 필터 결과를 화면이 기억한다 |

0.54초는 기동할 때 메인 스레드에서 도는 값이라 그대로 두면 앱이 늦게 뜬다.
33ms 는 필터를 만질 때마다 걸리는 시간이라 손에 걸린다.

## 6. 130개 팩을 어떻게 보여 줄 것인가

로테이션이 없으므로 **130개가 한 목록에 늘어선다.** 지금 상점은 10개를 세로로 늘어놓는 구조라
그대로 두면 못 쓴다. 로테이션 대신 **고르는 수단**이 필요하다.

- 시대(세트 묶음)로 접기 — 「Scarlet & Violet」, 「Sword & Shield」…
- 세트 이름 검색
- 값순·발매순 정렬

로테이션을 나중에 넣더라도 이 정리는 어차피 필요하다.

## 7. 그 밖에 흔들리는 것

- **컬렉션 진행도가 「90 / 20,479」가 된다.** 모을 만한 목표로 읽히지 않으므로 세트별
  진행도로 바꾼다
- **오리파 후보 풀**이 2만 장에서 뽑힌다. 부를 때마다 전체를 값순 정렬하는 코드가 있어 함께 고친다
- **도감**은 지금 10세트 카드로만 짜여 있다. 130개가 들어오면 새 도감을 만들 여지가 크지만
  이번 범위는 아니다. 기존 도감은 그대로 돈다
- **한번에 판매 임계값**(1,000~10,000원)을 새 시세 분포로 다시 잰다
- **팩값·도감 난이도·보상**은 전부 시세에서 나오므로 스냅샷을 갈면 다시 계산된다.
  기존 도감의 별과 보상이 움직일 수 있으니 대조표를 뽑아 확인한다

## 8. 작업 순서

| # | 일 | 크기 |
|---|---|---|
| 1 | 등급 17종 매핑 (카드 1,874장) | 작음 |
| 2 | 시세 수집 — 재시도·UA 보강, 174세트 | 작음 |
| 3 | 팩 가능 세트 선별 + 아트 137개 수집 | 중간 |
| 4 | 팩 아트를 번들에서 네트워크로 | 중간 |
| 5 | 성능 — 정렬 사전계산 + 필터 기억 | 중간 |
| 6 | 상점 화면 — 130개를 고를 수 있게 | 중간 |
| 7 | 한국어 결합(14,862) + 번역(5,600) | **큼** |
| 8 | 경제 재검증 + 컬렉션 진행도 | 중간 |

1~2 는 데이터 작업이고, 3~6 은 앱이 규모를 견디게 만드는 일이며, 7 이 가장 크다.

## 9. 두 판으로 나눈다

**7번(한국어)이 나머지 전부를 합친 것보다 크다.** 한데 묶으면 앞의 것들이 한국어 작업이
끝날 때까지 나가지 못한다.

- **1판** (1~6, 8): 팩 130개를 전부 판다. 새 세트의 카드 이름은 영문으로 나온다
- **2판** (7): 한국어를 채운다

다만 「출시할 때는 항상 한국어로 낸다」고 하셨으므로, 1판을 영문 이름으로 내는 것이 그 원칙과
어긋난다. 두 가지 중 하나다.

- **가** — 한 판으로 묶어 한국어까지 끝내고 낸다. 나가는 시점이 그만큼 늦다
- **나** — 1판에서는 **한국어가 채워진 세트만** 판다. 결합으로 덮이는 만큼(약 73%)이 먼저
  나가고, 번역이 끝나는 대로 나머지 세트를 여는 2판을 낸다

「나」를 권한다. 앱에는 영문 이름 카드가 한 장도 없고, 파는 팩은 10개에서 90개 이상으로
늘어난다. 결합은 기계 작업이라 번역보다 훨씬 빨리 끝난다.

## 10. 결정 결과

1. 한국어까지 한 판으로 묶어 영문 이름 카드 없이 낸다
2. 팩 아트는 네트워크 캐시로 돌린다
3. 상점은 카드 데이터의 시리즈를 기준으로 묶는다
